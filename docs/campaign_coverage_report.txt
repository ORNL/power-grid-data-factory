--------------------------------------------------------------------------------
GENERATION METHODOLOGY (common to both campaigns)
--------------------------------------------------------------------------------
Both datasets were produced by the adaptive, coverage-constrained, multi-fidelity
"ultrascale" sampler. Per seed grid, the pipeline expands one base case into
millions of labeled AC-OPF instances:

1. Seed grids
   Canonical pglib-opf cases (plus a few synthetic grids as probes in v1).

2. Operating-point synthesis
   For each grid, operating points are drawn across 14 operating regimes
   (baseline, low_load, shoulder, summer_peak, winter_peak, high_renewable,
   low_renewable, high_import, high_export, maintenance, branch_derating,
   generator_cost_shift, reactive_stress, extreme_peak) using space-filling
   designs (Sobol, Latin-hypercube, stratified, regime-specific, time-series).
   Each point perturbs global + regionally-correlated + local-residual load,
   renewable scale, reserve margin, branch ratings, and cost.

3. Topology variation
   Baseline plus single-line switching, double-line switching, and maintenance
   configurations (N-1 / N-2 branch removals).

4. Contingencies
   Credible N-1 / N-2 branch outages selected via an ontology-driven,
   state-aware constrained beam search (beam width 32).

5. Screening
   DC-based severity features (dc / voltage / reactive risk) with multi-trigger
   escalation (uncertainty multiplier 2.33) prioritize informative, near-boundary,
   active-constraint-novel candidates.

6. Acquisition / selection
   A portfolio budget split across queues (broad_coverage 0.22,
   active_constraint_novelty 0.20, security_boundary 0.20, credible_contingencies
   0.16, high_severity_and_uncertainty 0.12, unscreened_audit 0.10) under
   portfolio caps (max_per_grid, max_per_regime, max_per_contingency_class).
   When budget >= candidate count, all constraint-passing candidates are taken
   ("full-budget").

7. Solve & label
   Every candidate is solved as AC-OPF with PowerModels + Ipopt, and every result
   is retained regardless of termination status, producing a labeled
   feasibility-classification corpus (feasible = LOCALLY_SOLVED /
   ALMOST_LOCALLY_SOLVED / OPTIMAL; infeasible = everything else). Execution is
   map/reduce over 8192 shards / 1024 MPI ranks; the reduce stage dedups into
   ledgers + a reduce report.

Two counting levels appear below:
   - Selected candidates = distinct (grid, operating-point, topology, contingency)
     instances chosen (one reduce-report "solved" entry each).
   - Raw sample rows = every solver output row written to samples.jsonl (each
     candidate expands to a base + contingency solves, ~3x the candidate count);
     this is the actual training corpus.
